Оптимизация Canvas-анимаций: 60 FPS на любом устройстве

Введение

Когда мы создаём анимированный мультик на Canvas — например, наш проект «Пирожки с нуля», где кипит вода, летит пар и двигается шеф-повар — всё это должно выглядеть плавно. Целевой показатель — 60 кадров в секунду (FPS). Если анимация «фризит» или дергается, зритель теряет интерес уже через первые секунды. В этой статье разберём ключевые приёмы оптимизации Canvas-анимаций, которые позволят добиться плавного движения на любом устройстве — от мощного десктопа до бюджетного смартфона.

1. requestAnimationFrame vs setInterval

Самая распространённая ошибка новичков — использование setInterval или setTimeout для отрисовки кадров:

setInterval(() => draw(), 16); // ~60 FPS

Этот подход имеет несколько серьёзных проблем. Во-первых, setInterval не привязан к частоте обновления экрана: если монитор работает на 75 Hz, анимация будет отрисовываться с «ATAR» — лишние или пропущенные кадры. Во-вторых, даже если вкладка браузера неактивна, setInterval продолжает работать, зря расходуя ресурсы CPU и батареи.

Правильное решение — requestAnimationFrame:

function animate(timestamp) {
  ctx.clearRect(0, 0, canvas.width, canvas.height);
  drawScene(timestamp);
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

requestAnimationFrame привязан к частоте обновления экрана и автоматически приостанавливается при переключении вкладки. В нашем проекте «Пирожки» вся основная функция рендеринга — drawScene — вызывается именно так, что обеспечивает плавное движение пара, бурление воды и анимации шефа.

2. Ограничение количества частиц

Пар из кастрюли — это частицы: десятки или сотни мелких полупрозрачных эллипсов. Каждая частица требует вызова ctx.beginPath, ctx.fill,.ctx.closePath. Чем больше частиц — тем больше работы для GPU/CPU.

Оптимальная стратегия — лимит частиц. В нашем проекте мы ограничиваем максимальное количество частиц на сцене (например, до 20–30 одновременно). Когда частица «умирает» (выходит за пределы экрана или таймер жизни истёк), она удаляется из массива и может быть переиспользована для новой.

particles = particles.filter(p => p.life > 0);
if (particles.length < MAX_PARTICLES) {
  particles.push(createParticle());
}

Также стоит уменьшать радиус и detail частиц на слабых устройствах. Простая эвристика: если FPS падает ниже 30 за последние несколько кадров — автоматически уменьшаем количество частиц.

3. Оптимизация redraw: только изменённые области

В Canvas 2D нет встроенного механизма «dirty regions» (как в jQuery). Каждый кадр мы перерисовываем весь холст с помощью clearRect. Это может быть дорого, если сцена большая.

Приём 1: частичный clearRect. Если анимируется только небольшая область (например, бурление воды в миске), не нужно очищать весь холст — очищайте только bounding-box этой области:

ctx.clearRect(0, waterTop, canvas.width, waterHeight);

Приём 2: двойная буферизация. Создаём offscreen canvas, рисуем на него, а затем копируем результат на основной canvas с помощью drawImage. Это снижает мерцание.

Приём 3: отложенная отрисовка (lazy rendering). Если сцена статична — не перерисовывайте её. В проекте «Пирожки» финальный экран с рецептом и таймингом — статичный. Как только данные отрисованы, анимационный цикл останавливается.

4. Object Pooling: переиспользование объектов

Каждый вызов new Object() — это выделение памяти, которое рано или поздно приведёт к сборке мусора (GC pause). В анимации пауза GC = дёрганый кадр.

Object pooling — это паттерн, при котором мы заранее создаём пул объектов и переиспользуем их:

const pool = [];
function getFromPool() {
  return pool.length > 0 ? pool.pop() : new Particle();
}
function releaseToPool(p) {
  p.reset();
  pool.push(p);
}

В нашем проекте частицы пара и пузырьки воды идеально подходят для пулинга: они создаются и уничтожаются десятки раз за сцену, но их структура одинакова.

5. Профилирование через DevTools

Прежде чем оптимизировать, нужно найти узкое место. Chrome DevTools提供了 мощные инструменты:

— Performance面板: записываем сцену, смотрим, какие функции занимают больше всего времени. В проекте «Пирожки» мы можем обнаружить, что drawSteam вызывается 50 раз за кадр, но каждая отрисовка — тривиальна, а вотalculateSteamPositions» тяжёлая из-за тригонометрии.

— FPS meter: включаем в DevTools (More tools → Rendering → Frame rendering stats) и смотрим реальный FPS.

— Memory面板: отслеживаем утечки памяти. Если массив частиц растёт бесконечно — значит, мы не удаляем мёртвые частицы.

6. Мобильные устройства: уменьшение разрешения

Retina-дисплеи и экраны с плотностью 2x, 3x — красиво, но дорого. Canvas размером 1920×1080 на экране iPhone с пиксельной плотностью 3x实际上意味着 рендеринг в 5760×3240. Это колоссальная нагрузка.

Решение: уменьшаем devicePixelRatio для мобильных устройств:

const dpr = Math.min(window.devicePixelRatio || 1, 2);

Также можно просто уменьшить размер canvas:

canvas.width = 640;
canvas.height = 360;

И растянуть его через CSS:

canvas { width: 100%; height: auto; }

В проекте «Пирожки» на мобильных устройствах мы ограничиваем разрешение до 2x, что снижает нагрузку в 2–4 раза при минимальной потере качества.

7. Lazy rendering и кэширование

Статичные элементы (фон, миска, стол) можно нарисовать один раз в offscreen canvas и потом просто копировать:

const bgCanvas = document.createElement('canvas');
const bgCtx = bgCanvas.getContext('2d');
// рисуем фон один раз...
// в основном цикле:
ctx.drawImage(bgCanvas, 0, 0);

Это особенно эффективно для сцен, где 80% кадра статичны и только 20% анимированы (например, кипящая вода в неподвижной миске).

Заключение

Оптимизация Canvas-анимаций — это не про «написать быстрый код», а про грамотное управление ресурсами. requestAnimationFrame вместо setInterval, пулинг частиц, частичная перерисовка, уменьшение разрешения на мобильных — всё это в совокупности позволяет нашему мультику «Пирожки с нуля» работать плавно на любом устройстве. Не забывайте профилировать: никогда не оптимизируйте то, что не является bottleneck.
