# H03 — Собственный Canvas2D-конвейер как «полиномиальный рендерер»

**Статус:** prototyped (`web/js/scene3d.js`, коммит a44c988) · **Каталог:** внешние гипотезы PolyArt

## Abstract

`polyart_3d.py` ends at wireframes because matplotlib draws lines.
A minimal hand-written pipeline on HTML5 Canvas2D — rotate, project,
painter's sort, Lambert, fog — is enough for *shaded* polynomial scenes
at 60 FPS with zero dependencies. WebGL/three.js is not required to
reach a presentable 3D for PWTP demos.

---

## 1. Гипотеза

Для типичных полиномиальных сцен (≤10k граней) алгоритм художника с
Ламбертом и туманом на Canvas2D даёт устойчивые 60 FPS и «достаточно
AAA» картинку (свет + глубина), при объёме кода <300 строк — и это
честнее духу PolyArt, чем тащить трёхмерный движок ради коэффициентов.

## 2. Упоминания

- `articles/20_3d_polynomialRendering.txt` → вращение/перспектива/изолинии;
  наш шаг дальше — затенение, которого в модуле нет;
- `presentations/04_gaming_application.txt`, `05_vr_ar_application.txt`
  → PWTP-демо должны запускаться «на любом устройстве»: Canvas2D есть
  везде, WebGL — не везде, three.js — лишний вес;
- `codec_javascript/polyart_codec.js` → софтверный растеризатор уже
  существует для Node; Canvas2D — тот же подход с ускорением браузером.

## 3. Что сделано в прототипе

`web/js/scene3d.js` (см. репо ax_game_wt):

| Этап | Реализация | Стоимость |
|---|---|---|
| Меши | параметрические сетки: тор, сфера, Кляйн figure-8 | генерация <5 мс |
| Террейн | Грей–Скот 128², 700 шагов, двойной буфер | ~120 мс однократно |
| Трансформ | yaw/pitch поворот, перспектива `f = W·0.9/z` | O(V) |
| Отсечение | backface по видовой нормали (замкнутые тела) | O(F) |
| Сортировка | художник по средней глубине квада | O(F log F) |
| Свет | Ламберт + hemispheric ambient 0.34 | O(F) |
| Атмосфера | линейный туман к цвету фона | O(F) |

Замеры прототипа: тор 34×18 → 60 FPS; террейн 87×87 → 45–60 FPS
(ноутбук 2020 г., интегрированная графика).

## 4. Выводы для апстрима

1. **Пайплайн переносим в Python** один-в-один (numpy вместо JS-массивов):
   `Scene3D.render_shaded()` мог бы стать аддитивным методом рядом с
   каркасным рендером `polyart_3d.Scene3D`.
2. Двойная буферизация обязательна: in-place Грей–Скот уходит в NaN
   (проверено смоук-тестом).
3. Неориентируемые поверхности (Кляйн) нельзя чистить backface-кулем —
   дыры на самопересечениях.
4. Нормали нужно переводить в видовое пространство тем же поворотом,
   что и вершины (иначе свет «приклеен» к объекту).

## 5. Как проверить воспроизводимость

```
открыть web/index.html -> вкладка 3D
объекты: torus / sphere / klein / terrain
метрика HUD: FPS >= 55 на торусе, >= 40 на террейне
визуальный критерий: непрерывность силуэта при вращении,
отсутствие «дыр» у Кляйна, туман скрывает дальний край террейна
```

## 6. Риски

- Художник не решает пересечения граней (только сортировка) — для
  самопересекающихся сцен возможны артефакты порядка;
- Нет антиалиасинга путей при плотной сетке → муар; лечится шагом сетки
  или `ctx.filter` (медленно);
- На слабых мобильных CPU террейн 700 шагов может дать паузу загрузки —
  считать в Web Worker или снизить до 400.
